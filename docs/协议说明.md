# 协议与逆向要点

> 本文记录重写这套客户端时确定下来的协议事实。所有结论都来自对 **`com.huachenjie.shandong_school` v8.7.7**
> 的静态分析与**服务端常量交叉验证**（例如字段密文逐字节一致），不是猜测。
> 常量集中放在 `sdlab/constants.py`，任何改协议的动作只改那一个文件。

## 0. 总览

```
登录/备跑         记录（本地）                      上传（分批）                结算
loginCheck   ─┐                                    uploadRunRecord★  ─┐
滑块验证码     ├→ startSunRun_v2 → points/steps/paces → uploadStepsRecord ├→ finishSunRun_v2
loginPassword ┘   （拿记录号与打卡点）               uploadPaceRecord   ┘   （服务端复核）
                                                    uploadPassPoint
```

* 基址：`https://api.huachenjie.com/run-front`
* 鉴权：登录后服务端下发 `token` / `satoken`，此后所有业务请求放在请求头里（`Authorization` / `satoken`）。
* **只有 `run/uploadRunRecord` 需要 `sign` 签名**（`Endpoint.need_sign=True`），其余接口不校验。
* 常量版本：`APP_VERSION="8.7.7"`、`BUILD_VERSION="26101017"`、`APP_CODE="SD001"`。

## 1. 公共字段与请求头

每个 POST body 都带这 9 个公共字段（`Transport.base_payload()`）：

| 字段 | 说明 |
| --- | --- |
| `modelName` / `systemVersion` / `platform` | 机型、系统版本、平台，来自设备指纹配置 |
| `appVersion` / `buildVersion` / `channel` / `appCode` | 版本与渠道 |
| `deviceId` | 设备号，**由 12 个 `Build` 字段长度拼接后取 hash 而来**（见第 4 节） |
| `timestamp` | 毫秒时间戳，参与签名 |

请求头：`app`（应用标识）、`e`、`pv`、`Authorization`、`satoken`、`sign`（仅上传轨迹用）。

## 2. 签名（`crypto.get_sign`）

```
sign = AES-CBC( swap_ends( sha256_hex(body_json) ) , signKey , iv )
```

* `body_json` 必须与**实际发出去的字节完全一致**（紧凑分隔符，不转义非 ASCII）——
  传 dict 时用 `json.dumps(body, separators=(",",":"), ensure_ascii=False)`。
* `swap_ends(hex64)` 把 64 个 hex 字符按 `尾 8 + 中 48 + 头 8` 重排（自逆，解密同式）。
* `signKey = 8 字节明文密钥 + 16 个 0x00`（共 24 字节，走 AES-128-CBC 时只用前 16 字节）。
  生产密钥 `SIGN_KEY_PROD`，`env ∈ {9, 11}` 时用测试密钥 `SIGN_KEY_TEST`。
* 结果 base64，长度固定 **108 字符**（`transport.post(..., need_sign=True)` 自动加）。

## 3. 字段加密与滑块

| 用途 | 算法 | 密钥 / IV |
| --- | --- | --- |
| 手机号、密码等敏感字段 | AES-128-CBC | `FIELD_KEY` = `F44B0282BEA83557` + 16×00；IV = `01234ABCDEF56789` |
| 滑块验证码坐标 | AES-128-**ECB** | `SLIDER_KEY` = `Ukp3hmSe7BmMcgbE` |
| 结算码 `runImgRecord` | MD5(code + buildVersion + appVersion + `RUN_IMG_RECORD_KEY` + timestamp) | 32 位小写 hex |
| 部分 native 参数 | DES-ECB（8 组 8 字节密钥，按索引选） | `DES_KEYS` |

**滑块坐标伪装**（关键，服务端按伪装后的值比对）：
```
fake_x = int(raw_x - 6.5) + 16.5          # SLIDER_MARGIN=6.5, SLIDER_OFFSET=16.5
pointJson = AES-ECB(json({"x": fake_x, "y": 15.0}))   # y 固定 15.0
```

验证码流程（**已对真实服务端实测通过**，`scripts/realcheck.py` 5/5 一次挑战内过）：

```
captcha/get  {"captchaType":"blockPuzzle"}  → originalImageUrl / jigsawImageUrl / token
   ↓  下载两图，用 alpha 通道裁出真缺口形状；缺口模板画在与背景图等高的画布上，
      所以 alpha bbox 的 top 就是缺口纵坐标 → 只在 ±4 像素的行带里做灰度 SAD 匹配
   ↓
captcha/check {"captchaType":"blockPuzzle", "token": …, "pointJson": AES-ECB({"x": 缺口x + 10, "y": 15})}
```

★ **两个必坑点**（早期就是在这里绕了很久）：

1. `captcha/check` **一次性**——每调一次就消费掉该 `token`。失败重试必须重新
   `captcha/get` 换新挑战，**不能在同一个 token 上换坐标重试**（否则表现为「全 x 扫描零命中」）。
2. 明文里的 `x` 必须带 **+10** 的滑块留白补偿（`crypto.encrypt_slider_point()` 已内置），
   直接提交缺口原始像素会被判错。

密钥来源也已在反编译里定案：`JavascriptApi.java:656` 的 `V(handler, "secretKey", "Ukp3hmSe7BmMcgbE")`
即 H5 `CaptchaVerifyPage` 从原生桥拿到的就是这把固定密钥（与 `SLIDER_KEY` 同一个值）。

**交叉验证**：`crypto.encrypt_field("13800138000") == "WQZsdeHd/SBQZ8ZhmJzWhg=="`，
与服务端回显常量逐字节一致 ⇒ 纯标准库 AES 实现正确。

## 4. deviceId

App 里设备号是三层降级：能取到 `Build` 字段就按 `model/brand/manufacturer/device/product/board/
hardware/display/id/bootloader/fingerprint/radio` 十二项**长度的个位数**拼成一个串，再做 Java 风格 `hashCode`；
取不到则退回随机串。`simulator.build_device_fingerprint(cfg)` 复刻了这条逻辑，长度 16。

## 5. 一次阳光跑

### 5.1 开跑（`run/startSunRun_v2`）

九参数，**顺序固定**（错一位服务端就当作别的字段）：

```
schoolCode, fenceCode, activityCode, lat, lng, minRunDis, useCreditSword, runPlanCode, sportType
```

返回里给出记录号 `runRecordCode` 与打卡点 `targetPoints`（客户端写入本地库，作为轨迹生成的目标点）。

### 5.2 记录

| 本地表 / 报文 | 采样 | 内容 |
| --- | --- | --- |
| `points` / `pois` | 3 秒一点 | lat、lng、runTime、collectTime、state、offFenceDisM、isValid |
| `steps` / `stepList` | **20 秒一段** | startStep、endStep、startTime、endTime、step、time |
| `paces` / `paceList` | **每 50 米一段** | distance、start/endDistance、stepCount、time、pace |
| 步幅 | 同上 | `strideList` + `strideInterval` |

`stepInterval` / `paceInterval` 的默认值就来自 `com.huachenjie.common.bean.CommonConfig`：
`stepInterval = 20`（秒）、`paceInterval = 50`（米）、`poiInterval = 15`（轨迹上传节流秒）、
`validDistance = 25`（打卡半径米）、`sensitiveDistance = 45`、`runFilterAccuracy = 50.0`（精度上限米）、
`gpsFilterAccuracy = 150`（GPS 白名单模式）、`strideStatisticsInterval = 100`。

### 5.2.1 原版记录链路（本项目 `sdlab/walker.py` 逐项对齐）

定位回调每 **3000ms** 一次（`LocationComponent` → `lj0.m(context, 3000L, …)`），每次造一个
`RunLatLng` 并进入 `DataComponent.W1()`：

1. 与**上一个有效点**算球面折线距离，`BigDecimal` 四舍五入到整米；
2. 若 `offFenceDisM >= 0` 则扣掉一段（`jLongValue -= offFenceDisM`），负数归零；
3. 过滤 `H0()`：精度超限丢弃（普通 50 米 / 白名单 150 米）；`speed < 0` 且上一点也 `< 0` 丢弃；
   与上一点时间差 > 0 且折算速度 > **10.438 m/s**（≈ 37.6 km/h）丢弃；
4. 通过者 `setValid(true)` 并计入距离，未通过者 `isValid=false`；
5. **无论是否通过都 `i0()` 落库**（所以 `points` 必须有 `is_valid` 列），但只有有效点参与折线累距。

轨迹上传有门限：取 `state in (INIT, FAIL) and isValid=1` 的点，**超过 3 个**才发（`c0()`），
置 `UPLOADING` 按 200 个一批；配速/步频段则**少于 3 段不发**（`b0()` / `d0()`）。

时间字段的单位是**跑步内秒**（`Q0() = (currentTime + saveCurrentTime) / 1000`），不是毫秒——
`IntervalStep.setEndTime` 会把 `time = endTime - startTime`，`IntervalPace.setEndDistance` 会把
`distance = endDistance - startDistance`，两者都是原版的联动语义。

只存在本地、**不上传**的字段：`accuracy`、`speed`、`satellites`（原 App 里标了 `serialize=false`）。

上传是**分批**的（默认 `DEFAULT_UPLOAD_BATCH=50`）：`uploadRunRecord` 每批成功后服务端按
`indexList` 回执；客户端把状态位从 `STATE_UPLOADING(2)` 改成 `STATE_SUCC(8)` 或 `STATE_FAIL(4)`。

状态位：`STATE_INIT=1`（待上传）、`STATE_UPLOADING=2`、`STATE_FAIL=4`、`STATE_SUCC=8`。

### 5.3 结算（`run/finishSunRun_v2`）

结算报文一次性带上 `runRecordCode / duration / dis / totalStep / status / stepInterval /
paceInterval / targetPoints / alignType / pauseCount / pauseTimes`，并且**只带未上传成功的那些点**
（外加尾部补齐段），同时附上 `pois`、`stepList`、`paceList`、`runImgRecord`。

服务端回 `status`（1 通过 / 0 不通过）与 `invalidReasons`（失效码）。

### 5.4 客户端本地判定（复刻 `DataComponent.W0`，判定顺序不能换）

| 顺序 | 规则 | 失效码 |
| --- | --- | --- |
| 1 | GPS 有效性（`GPS_STALE_MS=15000`，无定位直接失效） | `25` |
| 2 | 分段步幅异常段数 > `segmentStrideExceptionNum` | `58` |
| 3 | 距离不在 `[singleMinDistance, singleMaxDistance]`（默认 1000~10000 米） | `2` |
| 4 | 打卡点：`clockMode==1` 按 `requiredPointCounts`/`optionalPointGoalCounts`，否则按 `targetPoints` 总数 | `1` |
| 5 | 配速越界（`minPace` 过快 / `maxPace` 过慢） | `3` |

对应实现：`protocol.evaluate_run(...)` → `RunValidity(is_valid, reasons, distance_m, pace_s_per_km,
checkpoints_done, total, status)`，`status` 是 **property**。

## 7. 服务端复核（Mock 里也照做了）

`mock.py` 不只是回 `code:0`，它按规则**真的复核**一遍：距离区间、配速区间、打卡点命中、
围栏外点数、`runImgRecord` 一致性——不通过就回 `status=0` 与对应的 `invalidReasons`。
这样才能验证客户端的判定链是否与真实服务端一致。

## 8. 复现顺序建议

1. `sdlab/crypto.py` 的自检（字段密文、签名长度、滑块伪装、结算码）——**必须逐字节对上**；
2. `sdlab/mock.py` 起本地服务端，跑通登录链路；
3. `sdlab/engine.py` 一次完整跑步：轨迹 → 分段 → 上传 → 结算；
4. 最后才是对着真实服务器验证（默认不做，且请自行评估风险）。
